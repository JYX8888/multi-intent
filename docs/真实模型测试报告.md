## 2. 判定标准

每条请求同时检查：

1. HTTP 状态是否为 `200`；
2. 响应是否为合法 JSON；
3. 是否严格包含 12 个固定字段；
4. 六个意图布尔字段是否符合预期意图；
5. `*_content` 是否满足启用时为字符串、未启用时为 `null`；
6. 是否出现遗漏或额外意图。

## 4. 汇总

- HTTP 成功：10/10
- 合法 JSON：10/10
- 固定 Schema：10/10
- 意图集合完全匹配：7/10
- 存在意图遗漏：0/10
- 存在额外意图：3/10

结论：当前服务已经能够稳定返回固定格式 JSON，且多意图抽取基本有效；但还不能认为十条业务测试全部通过。主要问题不是 JSON 结构，而是否定表达的意图边界。

## 5. 失败用例分析

### 第 3 条

模型将“昨天晚上没吃东西”识别为饮食意图。该文本确实涉及饮食行为，但本测试预期只把明确的饮食记录或饮食咨询视为 diet，因此需要进一步明确业务规则：是否记录“没吃东西”也属于饮食意图。

### 第 4 条

模型将“今天没称体重”和“没有测尿酮”分别识别为 weight、ketone。当前业务预期是：否定“没有测量”不应产生对应数据分析意图。Prompt 需要明确区分“存在业务数据”和“明确说明没有数据”。

### 第 10 条

模型将“今天没有运动”识别为 exercise。当前业务预期是不记录没有发生的运动，因此需要增加否定表达规则。

## 6. 首次联调问题

第一次真实调用全部返回 `408`。原因是 HTTP 路由监听了 Node.js `IncomingMessage` 的 `close` 事件；正常请求体接收完成时该事件也可能触发，导致模型调用被误取消。

已改为监听 `request.aborted`。修复后重新测试，10 条请求均返回 `200`。

## 7. 建议的下一步

在继续接入 Dify 前，建议先更新 Intent Planner Prompt 和校验规则：

- 明确“没有称体重/没有测尿酮/没有运动”不代表对应意图；
- 明确“没吃东西”是否属于 diet；
- 对否定词和缺失数据建立测试集；
- 将 3 个失败用例加入自动化回归测试；
- 保留 Schema 校验，防止模型返回解释文字或额外字段。
